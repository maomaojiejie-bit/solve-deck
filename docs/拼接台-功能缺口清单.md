# 拼接台功能缺口清单（我逐项对着代码与页面点过）

> 结论先说：**骨架是对的，缺的是「覆盖面」和「用户真能做的动作」**。
> 下面每条都带证据（源码行号或 DOM 观测），不带"应该大概"。

---

## 一、覆盖：28 型里只有 7 型能进

`src/core/lab/picks.ts` 的 `PICKS` 只有 7 个键：

```
A3, A5, A6, A1, M3, M3-cantilever, S5
```

| 科目 | 已有 | 缺 |
|---|---|---|
| 电路 A1–A7 | A1 / A3 / A5 / A6 | **A2 / A4 / A7（3）** |
| 数字 D1–D6 | 0 | **D1–D6（6）** |
| 材料力学 M1–M8 | M3 / M3-悬臂 | **M1 / M2 / M4 / M5 / M6 / M7 / M8（7）** |
| 理论力学 S1–S7 | S5 | **S1 / S2 / S3 / S4 / S6 / S7（6）** |

**缺 22 型。** 其余 21 型打开 `#/lab/t/<id>` 会怎样，还没验证（可能出"本题不适用"卡，也可能白屏）。

代价：每型 = 一张 `pick` 表（把图上的器件映射回参数）+ 一条「骨架不改 → 与快照逐键相等」的往返断言。按现有代码密度估 **25 分钟/型 ≈ 9 小时 ≈ 2 天**。这是"补全功能"里最贵的一块，但也是最有说服力的一块——它证明求解内核真的通用，而不是给 7 道题做了 7 个特例。

## 二、用户能做的动作：8 个操作，UI 只露出 5 个

`src/core/lab/types.ts` 的 `GraphOp` 有 8 个：

| op | 作用 | UI 有没有 |
|---|---|---|
| `deleteDevice` | 删器件 | ✅ 每行一个「删」 |
| `addDevice` | 加白名单器件 | ✅「加入器件」按钮组（+R/+V/+C/+D/+Q2/+M2 与三种支座） |
| `addEdge` | 两次点击两个 pin 连线 | ✅ 下拉 + 两次点击 |
| `addSupport` | 加支座 | ✅ 力学「加入器件」 |
| `addLoad` | 加载荷 | ✅ |
| `changeKind` | 改器件种类 | ⚠️ **只有支座**有下拉；电阻/电容/电源没有（想改 R→C 做不到） |
| `setSemantic` | 标语义 | ✅ 每行一个下拉（但选项只有 5 个，见第三节） |
| `applyParams` | 参数表改动写回图 | ✅ 改数值即回写 |

**缺的动作（要新增 op，不只是加按钮）：**

1. **力学族的杆件/梁段完全不可操作** —— 我把 `#/lab/t/S5` 的「画布器件」拉出来看，只有三条：`n-sup-A`、`n-sup-B`、`n-load`。**三根杆 AC/AB/BC 一条都不在列表里**，也不能加杆。
   于是 W8 宣传的「删一根杆 → `m≠2j-3` → 拒绝」在界面上走不到；`check:assemble` 第六个用例之所以绿，是因为它直接调 `reduce()` 绕过了 UI。**门禁绿、用户做不到，比红更糟。**
2. **改截面不可做**：`A / I / E` 没有输入口，只能靠骨架默认值。M1/M2/M7 一旦进 lab，截面是它们的主参数。
3. **拖动节点**：`editable` / `onNodeMove` / `data-draggable` 在 `SpecGrid.tsx` 里 **0 处**，lab 与结果页都不可拖。
4. **撤销 / 重做**：没有。删错一个器件只能「换一个题型」重来（那会清空全部改动）。
5. **清空 / 恢复骨架**：只有换题型，没有「恢复这张骨架的原始状态」。

## 三、语义标签：源码里就是 5 个，少 3 个

`src/pages/Lab.tsx:32`：

```ts
const SEMANTICS = ['unknown', 'bias', 'coupling', 'bypass', 'supply'];
```

规格是 8 个（`unknown / bias / coupling / bypass / supply / load / feedback / stage_link`）。

后果不是"少几个选项"，而是**判据链断在那**：

- A3 的 `Rl` 只能标 `unknown` → `semantic` 永远不过 → **A3 在拼接台里必然落 N 档**，等效图永远不渲染，用户看到的永远是"数值照常给出、等效图待确认"。
- A7 的反馈电阻标不了 `feedback`，"反馈环"这条硬闸门永远不触发。

## 四、入口：只有首页有，结果页没有

grep 结果：

- `src/pages/Home.tsx` → 有 `href="#/lab"` ✅
- `src/pages/Result.tsx` → **0 处** ❌
- `src/pages/Solve.tsx` → **0 处** ❌

也就是说：用户解完一道题（结果页），发现"结果对不上题意"，**没有任何入口通往拼接台**。而 W9 的设计里，`#/solve` 本来就该给两个出口（「看结果 →」/「去拼接台改结构 →」）。

## 六、门禁的缺口

现有三道（182 / 27 / 23 项）都只验到 `reduce()` 这一层。缺：

1. **UI 动作序列**用例：删杆/加杆/连线这三件事必须**通过点页面**来做，而不是直接构造 op。
2. 拖动后 `params` 逐键不变（坐标不是模型）。
3. 三候选与既有快照逐位相等。
4. 语义标全后 tier 必须升到 F。

# 建议的批次

| 批次 | 内容 | 工时 | 为什么排这个顺序 |
|---|---|---|---|
| **W10-A** | 语义 5→8 + 关键标签表；S5 杆件进列表、加/删杆 op、改截面；Result/Solve 补拼接台入口；`check:assemble` 改走 UI；补「恢复骨架」 | 半天 | 全是"当场会踩到"的洞，且不需要新架构 |
| **W10-B** | 拖动 + 重算导线；生成 3 个候选；`?p=` 参数覆盖 | 1 天 | 你昨天点名的两个交互，依赖 W10-A 的 op 补齐 |
| **W11** | 覆盖补齐：22 型逐个加 `pick` 表 + 往返断言 | 2 天 | 最贵，但它是"通用"这个词的唯一凭据，放最后做不会拖累前两批 |

我不建议把 W11 和三候选混在一起做：一个改覆盖、一个改交互，混在一起的返工成本比分开高。
